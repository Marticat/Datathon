# Сдача результатов — orleugpt

Формат реализован по `CQA_Student_Guide_Appendix_Results.pdf`, версия 1.0.
Команда настроена в `submission.config.json`. Приложение и локальная модель должны быть запущены.

## DEV: 60 чатов и 5 звонков

```powershell
npm run submit -- dev --evaluate
```

Команда использует уже импортированную группу `DEV`, официальный чек-лист, оценивает весь набор, ждёт завершения, проверяет и записывает `results/dev/results.json`. Повтор команды продолжает сохранённую задачу; `--fresh` запускает новую. Если окно команды закрыто, сервер продолжает обработку. После перезапуска приложения очередь возобновляется.

## Контрольный набор: ровно 10 чатов

Когда организаторы дадут набор, сохранить исходный JSON локально, например в `.local/prod.json`. Не менять ID, порядок реплик, события и сообщения бота.

```powershell
npm run submit -- prod --input .local/prod.json --evaluate
```

Если организаторы подтвердили получение через прежний API и группу `PROD`, вместо `--input` можно использовать `--fetch`. Если имя группы другое — добавить `--group ИМЯ`. Адрес API с секретными параметрами остаётся только в `.env`.

Результат: `results/prod/results.json`. До получения настоящих 10 чатов файл не создаётся: пустой файл или вымышленные ID не являются сдачей.

## Проверка и отправка

```powershell
npm run submit -- dev --check
npm run submit -- prod --check
git add results/dev/results.json results/prod/results.json
git commit -m "Submit DEV and control evaluations"
git push origin main
git rev-parse HEAD
git ls-remote origin refs/heads/main
```

Последние две команды должны показать одинаковый хеш. Проверить доступ к обоим файлам по переданной организаторам ссылке. PDF требует **открытый репозиторий**; для приватного нужно заранее согласовать доступ или публичность. Эта команда не меняет видимость репозитория и сама не делает push.

Код выхода 0 — файл корректен и все записи успешны; 2 — корректный файл содержит ошибки обработки; 1 — команда не завершилась (формат, состав набора, сеть и т. п.). При ошибке проверки существующий файл не перезаписывается. Входной набор проверяется **до** импорта: девять новых чатов не могут дополниться старым десятым.

`--check` также использует локальную квитанцию `.local/submission-<набор>-export.json`: она связывает файл с исходными диалогами. Если файл, команда или исходный текст изменились, проверка потребует актуальную выгрузку. Квитанция остаётся локальной и не нужна жюри. После переноса проекта на другой ноутбук импортируйте исходный набор и заново выполните выгрузку, чтобы получить квитанцию.

## Что именно сдаётся

- Восемь официальных кодов: `contact`, `discovery`, `identification`, `consultation`, `empathy`, `dialogue`, `closure`, `critical`.
- Первоначальные AI-ответы; ручные решения по апелляциям не подменяют оценку модели.
- Числовые шкалы **до** применения веса: например `dialogue: 7`, а не `10.5`.
- `null` обозначает N/A только там, где оно разрешено. Итог пересчитывается по применимым весам и округляется до двух знаков. Грубое нарушение не обнуляет итог.
- Номера реплик с 1 по полному исходному транскрипту, включая клиента, бота и события. Если модель указала только проверенный диапазон, выгружаются номера всех реплик этого диапазона.
- Ошибки сохраняются отдельными записями `status: "error"`, с пустыми критериями и `score: null`. Для выбранной задачи сбой не заменяется прошлой успешной оценкой.
- Изменённые диалоги и оценки по изменённому чек-листу не выдаются за актуальный официальный результат. Название модели берётся из сохранённых оценок.
- Исходные транскрипты, аудио, служебное состояние, секреты и ссылки API не включаются в выгрузку.

Без `--evaluate` команда экспортирует уже сохранённые актуальные оценки, а отсутствующие отмечает ошибками. Для конкретного полного запуска: `npm run submit -- prod --job ID`. Внутренняя кнопка экспорта приложения сохраняет архив и **не заменяет** эту сдачу.

## Последний час

1. 0–5 минут: получить набор, проверить 10 уникальных исходных ID и запустить команду.
2. 5–40 минут: следить за прогрессом; время обработки зависит от длины диалогов, GPU и повторных попыток. Не запускать параллельно другие тяжёлые оценки/распознавание аудио.
3. 40–50 минут: проверить файл, разобрать ошибки, commit и push. Не ждать последней минуты.
4. 50–60 минут: проверить удалённый commit и доступность двух файлов; оставить запас на сеть.

Это бюджет времени, а не обещание скорости. DEV-прогон показывает реальное время на вашем ноутбуке.
